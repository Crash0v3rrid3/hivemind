Hivemind

A team memory that lives on every laptop and syncs through a folder.

No central server, no shared database to run or pay for. Each person keeps the whole team's memory locally and shares their own through Google Drive.

Why it exists

Shared memory, without a server to own

A shared, append-only, semantically-searchable team memory is a great idea — but the usual way to build one is a central service backed by one database that somebody has to stand up, secure, and keep running. On plenty of teams that central database is a non-starter, and nobody wants to operate a server just to keep notes.

Hivemind keeps the same idea and removes the center. Every developer runs a small node on their own machine. Records are written locally, exported as plain files into a shared Google Drive folder, and imported by everyone else. The result reads like one shared memory, but there is no shared infrastructure to run — only a folder the team already has.

What it solves

The problems it takes off the table

No central database

Nothing to provision, secure, back up, or bill. The only shared resource is a Drive folder; the sync medium is immutable files.

Stays inside the rules

Data lives on the team's own Google Workspace Drive and on local disks. No third-party or dedicated shared DB, so org data policy holds.

Real semantic search

Every record is embedded locally and indexed in a local vector store — embedded SQLite + sqlite-vec, or Postgres + pgvector — so search matches meaning, not just keywords, with the same query surface as a hosted tool.

Trustworthy authorship

Who wrote a record is derived from the Drive folder it came from, not from anything in the payload, so entries can't be forged as someone else.

Append-only history

Records supersede rather than overwrite; edits and deletes are new events. The full trail is preserved and auditable.

Works offline

A node is a complete copy. It keeps answering queries with no network; Drive just carries new files in and out when it reconnects.

How it works

One node per person, a folder in the middle

  1. Write, locally.

    A call to memory_add over MCP stores a record in your node's local database — embedded SQLite or Postgres — with a 384-dimension embedding computed on the spot.

  2. Export to your folder.

    The export loop serializes new local records to immutable NDJSON files in hivemind/<you>/<day>/ — the one subfolder only you can write.

  3. Drive syncs the files.

    Google Drive carries your files out and your teammates' files in. No service talks to another; the folder is the only channel.

  4. Import everyone else.

    The import loop reads peers' read-only subfolders, stamps each record with the author taken from the folder path, and ingests it into team_events — skipping anything already seen.

  5. Search the whole team.

    memory_search runs a vector query across your own and the team's records at once, returning ranked, de-duplicated results with tombstoned and superseded entries dropped.

Identity & trust

Authorship you can't fake

Drive sharing does the enforcement: your own subfolder is writable by you and read-only to everyone else. Because a record's author is derived from the folder it was imported from — never from a field in the record — no node can publish memory under another person's name. A node only ever writes as its configured owner, and the import side re-derives identity from the path on the way in.

Data model

Two tables, append-only

TableHoldsWritten by
local_eventsRecords authored on this node. The source of truth for your own memory, and what the export loop reads.memory_add, memory_update, memory_delete
team_eventsRecords imported from peers' Drive folders — the local cache of everyone else's memory.import loop
ingested_filesWhich NDJSON files have already been imported, so re-syncs stay cheap and idempotent.import loop

Edits and deletes are new events: an update supersedes its predecessor and a delete writes a tombstone. Search folds the history down to the current, visible view; nothing is destroyed. Embeddings are BAAI/bge-small-en-v1.5 (384-dim, via fastembed/ONNX — no PyTorch), indexed with an HNSW cosine index.

Running a node

Two ways to bring it up

A single CLI generates and operates the whole stack from one config file. Pick how it runs; the memory behaves identically either way.

Nix default · macOS

  • The app runs natively, supervised by process-compose — no Docker. Persistence is embedded SQLite, or a local Postgres.
  • Falls back to devenv when process-compose isn't available.
  • Pairs with Google Drive for Desktop: the folder is already on disk, so no mount daemon.

Docker portable

  • Docker Compose runs the app — with embedded SQLite or a Postgres container — from a locally-built image, nothing pulled from a registry.
  • Mounts Drive with the rclone FUSE container, or binds a Google Drive for Desktop folder.
  • The chosen backend is detected automatically, with Docker as the fallback.

Either way: init writes the config, setup prepares the node, up starts it, and doctor checks the mount, database, MCP endpoint, and the read/write boundaries between folders.
