# HiveMind 0.3 implementation plan

## Goal and authority
Implement the proposed 0.3 scope: hybrid search, bounded task context packs, sync visibility, and reproducible retrieval evaluation. SPEC.md remains authority for identity, append-only storage and visibility. This plan extends read APIs without changing the v2 event format. Prepare a reviewable feature branch; do not merge, tag or publish.

## Global Constraints
- Preserve wire schema v2, owner-derived authorship, identity/model binding, append-only writes, quarantine, and all existing visibility/filter semantics.
- Both SQLite and PostgreSQL must work. No required cloud service, LLM, model download, or new runtime dependency.
- Existing memory_search calls retain semantic behavior and response shape by default. New modes are explicit.
- Reject invalid inputs through the actual MCP dispatcher. Deterministic tie-breaking uses record IDs. Bounded responses must not expose embeddings or arbitrary record metadata.
- Sync telemetry is local observation, never proof of remote delivery. Do not expose credentials or raw exception messages.
- Implement sequential tasks with focused regression tests and independent task reviews. No merge, tag or publication in this scope.

## Task 1: Hybrid retrieval
Add app/hivemind_app/retrieval.py for portable lexical matching and reciprocal rank fusion helpers; extend repository.py, service.py and mcp_server.py. memory_search gains mode='semantic'|'keyword'|'hybrid', default semantic; invalid modes fail. Preserve existing list-of-record responses. Add an internal ranked search API for context packs carrying record, fused score and matched retrieval channels.
Use bounded query terms (max 32, normalized/lowercased (matching SQL lower; do not apply query-only NFKC/casefold), deduplicated), preserve code-ish identifiers/path/ticket tokens as well as words. Implement keyword candidates with parameterized SQL predicates and deterministic weighted match scoring on title, body, jira_ticket and tags on both backends; filter visibility and requested filters before ranking/limit. Literal %, _ and backslashes must never become wildcard syntax. Avoid loading the entire corpus into Python. Explain that this is lexical term matching, not BM25. Hybrid uses RRF constant 60, equal channel weights, pool max(200, top_k), deduplicates IDs; lexical-only matches survive fusion. Keyword mode must not invoke the embedder. Reuse shared candidate-filter helpers. Add SQLite behavioral tests plus PostgreSQL integration coverage for ranking/filtering, exact identifiers, punctuation, hidden/deleted/conflicted records, query validation, deterministic ties, and keyword without embedding. Add actual MCP-dispatch coverage for mode. Update SPEC search section.

## Task 2: Task context packs
Add context.py and memory_context(task, jira_project=None, jira_ticket=None, token_budget=2000, max_items=12), using Task 1 hybrid ranked retrieval. Strict integer token_budget 256..16000 and max_items 1..50; reject blank/oversize task. No repo filter yet: repository/file relations belong to later scope, current project/ticket filters are real existing fields.
Return a structured pack with task, items, estimated_tokens, token_budget, truncated and budget_method. Items include source_id, author, event_type, status, title, excerpt, timestamp, matched_channels and reason. Use original source excerpts only: no generated claims. Reasons explain retrieval channels and event category. Deduplicate identical normalized title/body across records, selecting deterministically. Keep relevance ordering; categories can be expressed per item, do not invent priority overrides. Never expose embedding or arbitrary metadata. Budget the entire serialized JSON response with a documented approximate UTF-8-bytes/4 estimator; ensure estimated_tokens <= token_budget including envelope. Trim/omit excerpts/items safely for Unicode, handle tasks too large for envelope with explicit validation error. Document estimator is not a tokenizer guarantee. Tests cover budget boundaries, long titles/tasks, Unicode, duplicates, filters, source attribution, hidden/conflicting records and actual MCP dispatch. Update SPEC and CLI usage instructions with read-before-work context tool guidance without writing automatically.

## Task 3: Sync status backend
Add sync_status.py with bounded in-memory per-process telemetry; expose GET /sync/status and MCP memory_sync_status(). Query repository aggregate counts for exact pending local exports (not bounded export batch length) and quarantined IDs. Track import/export last attempt, last successful cycle, last failure category, and import current-cycle failed/deferred files with relative paths and stable reasons. Cap displayed problem files to 20 and retain total counts. Include telemetry_started_at and loops_enabled; timestamps null before an attempt. Import partial success must be visibly degraded if any file/folder fails; root/roster failures must not appear successful. Keep existing import_once/export_once return contracts by optional observer/state arguments. Report local filesystem publication only; remote_delivery='unknown'. Do not claim acknowledgement or last successful peer delivery. No filesystem rescans triggered by status, no raw exceptions/absolute paths/record bodies. Add bounded recovery guidance appropriate to missing mount, parse/incomplete/provenance/import failure and conflicts without advising deletion. Tests cover startup/no loops, successful and failed cycles, partial failures, bounded telemetry, pending count beyond batch cap, conflicts, GET/MCP response and no secret leakage. Update SPEC.

## Task 4: Sync CLI
Add cli/src/commands/sync.ts and register 'hivemind sync status [--json]'. Call configured localhost MCP port GET /sync/status with finite timeout, validate schema/service identifier before displaying. Human output includes pending exports, quarantines, cycle health, per-process scope and remote delivery unknown; JSON prints the validated server response. Fail nonzero on unreachable/invalid endpoint, show clear action; degraded sync is clearly displayed (exit 1). No backend mutation or arbitrary host URL. Add tests with local HTTP server or injected fetch for success, degraded, invalid responses, timeout and config errors. Update cli README and relevant root quickstart documentation. Preserve lifecycle status command.

## Task 5: Retrieval evaluation and release preparation
Add an offline reproducible evaluation fixture with at least 12 queries over at least 24 memories covering decisions, blockers, exact code/path identifiers, tickets, synonyms and distractors. Implement an evaluator/script using production retrieval logic against real SQLite and a deterministic injected embedding fixture, reporting Recall@5 and MRR@5 separately for semantic, keyword and hybrid plus context-pack source coverage/budget compliance. Document that fixture embeddings test ranking behavior, not real-model semantic quality; provide optional real-model evaluation using an already-installed embedder without downloading in default CI. Expected relevance is explicit and independent of algorithm; include a regression threshold for hybrid exact-identifier retrieval and no visibility leaks. Add a CI-friendly make target and focused metric unit tests. Update README, CHANGELOG unreleased 0.3 notes and docs with examples, limitations and evaluator instructions. Bump all coupled app/CLI/runtime/template versions to 0.3.0, lockfile root only; do not change dependencies or historical changelog versions. Run full make check, build/package validation, and evaluation. Correct outdated touched SPEC overview text for SQLite/Nix where necessary. No release tag or publication.
